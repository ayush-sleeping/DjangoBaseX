# Tech Debt

**Every known defect, gap and deferred decision — ranked.** Check here before reporting something as
a new discovery; if it is listed, it is known.

Adding a row is part of the same change that creates the debt (`AGENTS.md` § 4). A row is closed by
striking it through with the date, not by deleting it — a deleted row loses the evidence that the
problem was real.

**Ranking:** 🔴 blocks a deploy · 🟠 will cause a real bug · 🟡 costs time repeatedly · 🟢 tidiness

| **DB-12** | 🟢 | **Postgres-only features pass locally on SQLite** | [ADR-0005](../adr/0005-sqlite-for-dev-postgres-by-url.md) accepts this. **Mitigated 2026-10-11:** CI runs the suite against PostgreSQL 16, so a Postgres-only behaviour with a test is caught before merge. **Mitigated further 2026-10-22:** `scripts/setup.sh` (BUILD_ORDER 4.1/4.4) develops against PostgreSQL 16 in Docker by default; only `--no-docker` and a plain host `runserver` stay on SQLite. Whether ADR-0005 should be superseded (settings default to Postgres) is an owner decision. Still silent locally, and for code with no test — set `TEST_DATABASE_URL` to a local Postgres when touching Postgres-specific behaviour |
| **DB-13** | 🟢 | **No seeders or fixtures** | Resetting local data means `createsuperuser` by hand. A `seed` management command would make it one repeatable step |
| **DB-14** | 🟢 | **`known-first-party` is a manual step** | Each new Django app must be added to `backend/pyproject.toml`. Forgetting it makes Ruff fail on files nobody touched — a misleading symptom for a trivial cause |
| **DB-16** | 🟡 | **No scheduler, so retention runs by cron** | `AUTH_BLUEPRINT.md` § 19.2 needs `auth_cleanup` run daily; `users_login_attempt` grows with attack traffic rather than user count. | **DB-17** | 🟡 | **A shared cache is a correctness requirement, not a performance one** | The permission-version counter, session liveness and every throttle live in `django.core.cache`, which defaults to per-process `LocMemCache`. `dbx.E005` (`BUILD_ORDER` **1.0**) refuses to boot that way with `DEBUG=False`, but until 1.0 lands nothing says so. `AUTH_BLUEPRINT.md` § 17.4 |
| **DB-21** | 🟡 | **Machine-caller authorization model undecided** | `API_DESIGN.md` says machine callers are principals with permissions. Decide and write the ADR before the first token endpoint. **Owner, 2026-10-11: decide later** — before the first API-token endpoint. |
| **DB-27** | 🟡 | **DB-11 describes the health view inaccurately** | `backend/core/views.py::HealthView` *does* run `SELECT 1` and answers 503 on failure — so `/api/health/` is an unbounded readiness probe (no timeout) documented as liveness, and it returns a hard-coded product name on an unauthenticated endpoint. DB-11 is left as written for the record; the fix is the three-rung design in `OBSERVABILITY.md` (`BUILD_ORDER` **6.2**) |
| **DB-29** | 🟡 | **Concurrency guarantees are Postgres-only; SQLite dev silently ignores them** | `select_for_update()` is a no-op on SQLite, and the planned audit-log triggers, exclusion constraints and independent audit connection only exist on Postgres. Numbering, ledger and audit tests must run in the Postgres CI job, never only locally. Extends **DB-12**. `DOMAIN_PRIMITIVES.md`, `DATA_LIFECYCLE.md` |
| **DB-32** | 🟠 | **`forgot/` is a timing oracle** | `POST /api/auth/password/forgot/` answers 204 for every address, but for an existing, active one it creates a token and sends the email before responding (`transaction.on_commit` runs inside the request without `ATOMIC_REQUESTS`). On SMTP the difference is a mail round trip, so response time reveals which addresses have accounts. Fix: enqueue the send (`BUILD_ORDER` 7.1, Celery) so both paths do the same work. See `AUTH_BLUEPRINT.md` § 6.7a |
| **DB-33** | 🟠 | **`MFA_ENCRYPTION_KEY` cannot be rotated** | TOTP secrets are encrypted with a single Fernet key (`users/mfa.py`). Changing the key makes every enrolled device undecryptable (`InvalidToken`), locking those users out of MFA sign-in. Fix: the `MultiFernet` encryption service with `rotate_encryption` (`BUILD_ORDER` **6.3**). Until then the key is effectively permanent; document it in the product's runbook |
| **DB-34** | 🟢 | **No QR code on MFA setup** | `/account/security` shows the secret and the `otpauth://` link but no QR, because adding a QR library is a `package.json` change. Users with phone authenticators must type the key. Add a small QR renderer (blueprint Ch. 16 already prefers frontend rendering) |
| **DB-35** | 🟡 | **Invitations have no role ceiling** | `POST /api/users/invitations/` (`users.invitations.send`) may invite into any non-elevated role, including roles granting more than the inviter holds, so inviting a second account is a way to widen your own reach. Elevated roles are guarded (§ 8.2). Decide whether a product needs "grant only what you hold" (the same question applies to `rbac.roles.assign`). See `AUTH_BLUEPRINT.md` § 10.2a |
| **DB-36** | 🟢 | **Turbopack's root is the whole repository** | `BUILD_ORDER` 3.5 needs it, so plugin frontends symlinked from `backend/plugins/` resolve. The dev watcher's scope therefore includes `backend/`, `.venv/` among it. The host dev server measured 327 MB RSS with the plugin linked, but there is no baseline to compare against. No narrower root exists while the two halves are siblings. A corollary: `frontend/node_modules` must be a real directory inside the repository, because Turbopack refuses a symlink that points out of its root (seen while rehearsing CI). If watching ever slows a large checkout, measure it first (with and without the plugin linked) before changing the layout. `CORE_ARCHITECTURE_PLAN.md` § 5 |
| **DB-37** | 🟡 | **Core's own screens are not in the navigation registry** | `GET /api/me/navigation/` and the home page's menu list only what plugins and `project/` register. Users, Roles and Account are reachable by link, but not from the menu. Register them from `users`/`rbac` `ready()` with their exact codes when 8.2 builds the shell and the route gate. `FRONTEND_PLATFORM.md` § 8 |
| **DB-38** | 🟡 | **A deliberate core edit in a product keeps core-guard red on `main` forever** | `core-guard.yml` (BUILD_ORDER 4.3) runs `core_doctor` over the whole tree, so drift that arrived by a merge fails the push to `main`, and every later PR then needs the `core-change` label too, even one that touches no core file. Once the label is routine it guards nothing. This is per `ENGINEERING_PRACTICES.md` § 52, but the steady state for a product that knowingly forked one file is unaddressed. Options: a reviewed `core-drift.allow` list in the product (path + SHA + reason) that the doctor honours, or accept it as pressure to upstream a seam. An owner decision |
| **DB-39** | 🟡 | **`core_doctor` reports every core file as modified on a CRLF checkout** | The manifest hashes bytes (§ 52: a line-ending change is real), and the repository has no `.gitattributes`. On Windows with `core.autocrlf=true`, every text file under a core tree differs from its SHA. Fix: a `.gitattributes` with `* text=auto eol=lf` (and `*.sh text eol=lf`), then regenerate the manifest |
| **DB-40** | 🟢 | **`test_setup_script.py`'s re-run test can flake on a busy host** | `test_a_rerun_keeps_every_secret_and_file_byte_for_byte` runs `setup.sh` twice against the real host's ports. If another process binds 8000/3000/5432 between the two runs, the second run correctly re-chooses a port and the byte-for-byte assertion fails. Seen once on 2026-10-22, then passed three times. Fix: a stub port probe in the test's sandbox |
| **DB-41** | 🟡 | **Setting changes are audited to the log, not to a table** | The settings registry (BUILD_ORDER 5.3) records every write and reset through `core.audit.log_activity("core.setting.changed", …)` with old → new. Until the ActivityLog table lands (BUILD_ORDER 6.4), that is a log line, not a queryable row, and CONFIGURATION § 9.11's row assertion is a `caplog` assertion. The call shape is stable, so 6.4 changes no caller |
| **DB-42** | 🟢 | **No metric when a setting read falls back** | CONFIGURATION § 9.6 wants `setting_resolution_fallback_total` whenever a read skips a scope on a DB, cache or coercion failure. No metrics facility exists yet, so 5.3 emits a structured `core.setting.fallback` warning log instead. Add the counter with the metrics work ([`OBSERVABILITY.md`](../system-design/OBSERVABILITY.md)) |
